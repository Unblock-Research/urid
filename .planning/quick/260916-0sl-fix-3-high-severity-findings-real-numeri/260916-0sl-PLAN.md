## Task 1 — Make the threshold predicate real (High #1)

**Problem (three layers):**
- `threshold` / `predicateEnabled` are chosen by the prover, and
  `predicateEnabled = 0` makes `predicateResult` unconditionally 1.
- `verify()` never cross-checks `publicSignals[3]` / `[4]` against the stored
  request, so a vacuous pass is indistinguishable from a real one.
- The comparison is against `claimValueHash`, a SHA-256-derived element of size
  ~2^254, while `GreaterEqThan(64)` requires inputs < 2^64. Enabling the
  predicate on any real claim fails witness generation. It has never been usable.

**Design — numeric claims:**

```
string  claim: valueHash = sha256("urid:claim-value:" + value) mod p   (UNCHANGED)
numeric claim: valueHash = poseidon([NUMERIC_TAG, numericValue])       (NEW)
leaf:          poseidon([nameHash, valueHash])                          (UNCHANGED)
```

Poseidon is cheap in-circuit, so the circuit can recompute the numeric
commitment and constrain it against the leaf's value half:

```
(poseidon([NUMERIC_TAG, numericValue]) - claimValueHash) * predicateEnabled === 0
clampedValue <== predicateEnabled * numericValue
geq(clampedValue, clampedThreshold)
```

The prover cannot substitute a different `numericValue` without breaking the
commitment, so `value >= threshold` becomes a statement about the credential
rather than about a hash.

**Files:** `circuits/merkle_inclusion.circom` (+ rebuilt artifacts),
`src/crypto/claim-encoding.ts`, `src/modules/credentials/credentials.service.ts`,
`src/modules/credentials/credentials.dto.ts`,
`src/modules/zk-proofs/zk-proofs.service.ts`, `src/crypto/CRYPTO-NOTES.md`.

**Also:** `verify()` cross-checks the threshold and predicateEnabled signals
against the stored request and returns `predicateEnabled` so a relying party can
tell a real bound from a vacuous pass. `prove()` rejects `predicateEnabled` on a
non-numeric claim instead of emitting a proof that cannot verify.

**Verify:** a credential with no numeric claims produces a byte-identical root to
the previous encoding (asserted, not assumed); a numeric claim proves
`>= threshold` and fails below it; a tampered numeric value cannot produce a
valid witness.
**Done:** `nPublic` stays 5; existing credentials need no re-mint.

## Task 2 — Client-side recovery custody (High #2)

**Problem:** `setupRecovery()` generates the secret server-side, Shamir-splits it
server-side, stores every ciphertext, and returns every guardian key in one
response; `recover()` then reconstructs and returns the plaintext secret. The
server sees the secret at setup and holds every input needed to rebuild it, so a
compromise yields everything. Calling this self-sovereign is not true.

**Design:** the server becomes an encrypted blob store.

```
setup   client: secret -> split -> encrypt per guardian
        POST { threshold, verificationTag, guardians:[{name,kind,encryptedShard}] }
        server stores ciphertexts only

recover GET /recovery/shards -> [{ shardIndex, encryptedShard }]
        client decrypts >= T with guardian keys and combines locally
```

**Files:** new `src/crypto/recovery.ts` (pure, exported: generate/split/encrypt/
decrypt/combine/tag — usable by a client and by tests),
`src/modules/identity/identity.service.ts`,
`src/modules/identity/identity.controller.ts`,
`src/modules/identity/identity.dto.ts`.

**Removed:** `IdentityService.recover()` and the reconstruct endpoint. Server-side
reconstruction is the capability being deleted, not relocated.

**Auth:** setup and status stay holder-authenticated (you still hold your key
when setting up). `GET /recovery/shards` is public — ciphertexts are useless
without guardian keys — and returns no guardian names.

**Verify:** a full round trip (split → store → fetch → decrypt → combine)
succeeds entirely client-side; the service never receives a secret or plaintext
share; fewer than T shares cannot reconstruct.
**Done:** no server code path can reconstruct the secret.

## Task 3 — Move Groth16 proving off the event loop (High #3)

**Problem:** `snarkjs.groth16.fullProve` runs 1–5 s of WASM on the request
thread. Node is single-threaded, so concurrent proofs queue behind each other
and every other route — health checks, verification, reads — stalls with them.

**Design:** a worker-thread pool with a bounded queue.

- `workers/prove.worker.js` — plain CommonJS, placed outside `src/` so it is not
  rewritten by `tsc` and resolves identically from `src/` and `dist/` (the same
  trick `getCircuitDir()` already uses for the circuit artifacts).
- `src/modules/zk-proofs/prover.pool.ts` — fixed worker count, bounded wait
  queue, per-job timeout, worker replaced on crash or timeout.
- Saturation returns 503 rather than queueing without limit, so the failure mode
  is a fast rejection instead of an unbounded backlog.

Configurable: `ZK_PROVE_CONCURRENCY` (default `min(2, cpus-1)`),
`ZK_PROVE_QUEUE_LIMIT` (default 16), `ZK_PROVE_TIMEOUT_MS` (default 30000).

**Verify:** the event loop stays responsive while proofs run (measured, not
asserted); a full queue returns 503; a timed-out job frees its slot.
**Done:** no proving work executes on the request thread.
