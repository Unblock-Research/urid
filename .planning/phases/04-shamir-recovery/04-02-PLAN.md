<interface_contract>
Reference these exact shapes when implementing; the test task (Task 1) encodes them.

- Library (installed in 04-01): `import { split, combine } from 'shamir-secret-sharing'`.
  - `split(secret: Uint8Array, shares: number, threshold: number): Promise<Uint8Array[]>` — returns N share byte-arrays; each share internally carries its x-coordinate.
  - `combine(shares: Uint8Array[]): Promise<Uint8Array>` — reconstructs the secret from >=T shares.
- Node built-ins only for symmetric crypto: `import { randomBytes, createCipheriv, createDecipheriv, createHash } from 'crypto'`. Cipher = `aes-256-gcm`, 32-byte key, 12-byte iv, 16-byte auth tag.
- Existing `RecoveryShard` columns available (from Phase 1, no migration): `encryptedShard String?`, `shardIndex Int?`, `threshold Int?`, plus `guardianName`, `guardianKind`, `status`.
- Serialized `encryptedShard` envelope (Claude's-discretion format — self-describing JSON string):
  `{ v: 1, alg: "aes-256-gcm", iv: <hex>, authTag: <hex>, ciphertext: <hex>, tag: <sha256(secret) hex> }`
  where `tag` is the non-secret verification commitment, stored redundantly on every row (same value across all shards, like `threshold`). The plaintext Shamir share is NEVER stored — only its ciphertext.

RECONSTRUCT FLOW (documented choice, per D/discretion in 04-CONTEXT): the guardian supplies their per-guardian AES key; the server looks up the stored ciphertext by shardIndex and decrypts it to recover the Shamir share, then combines. Rationale: this proves possession of the guardian key, keeps plaintext shares off the wire and out of storage, and makes garbled-share rejection a GCM auth check.
</interface_contract>
