<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → POST /api/identity/register | Untrusted input (handle, displayName, previously a spoofable `did`) crosses into identity creation |
| server → response body | The one-time private key crosses back out to the client (client custody) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Spoofing | identity.register() DID input | high | mitigate | Remove the external `did` param; derive the DID solely from the freshly generated public key (encodeDid). Self-cert test asserts decodeDid(did) === stored publicKey. |
| T-03-02 | Information Disclosure | private key handling | high | mitigate | Private key is returned exactly once, never persisted (encryptedPrivateKey stays null), and never written to logs. |
| T-03-03 | Tampering | stored publicKey vs DID | medium | mitigate | publicKey and DID are derived from the same keypair in one call; the self-certifying test proves consistency. |
| T-03-04 | Repudiation | DID registration event | low | accept | Ledger anchoring (register_did) provides a tamper-evident record; full audit trail hardening is deferred. |
</threat_model>
